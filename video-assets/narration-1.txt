Welcome to this behind-the-build walkthrough of PromptForge, a production AI prompt builder created with Manus AI. In this lesson, we will follow the complete journey: from the first product prompt, through interface design and feature development, to authentication, database connections, external platforms, deployment, SEO, analytics, and performance optimization.

Chapter one: start with a clear product brief. The first prompt described a professional AI prompt builder that could help creators turn rough ideas into polished instructions in under a minute. The important detail was not only the feature list. The brief also defined the audience, the Workshop Noir visual direction, the need for a dark industrial interface with orange accents, responsive behavior on mobile, and a real production deployment. A strong first prompt gives the building system both the job to do and the standard the result must meet.

Manus can then turn that natural-language brief into a working web project. The first build establishes the application shell, the routes, the builder experience, the shared navigation, and the visual system. Instead of beginning with disconnected screens, we give the product a consistent structure: a Builder for creating work, a Library for discovering proven prompts, account access for saved work and membership, and public pages for pricing, contact, and education.

Chapter two: shape the experience around the real workflow. On the Builder page, the user chooses what they are making, adds the audience and platform, sets the tone, and watches a structured prompt take shape. The output is organized into practical fields such as role, task, audience, format, and constraints. This is more useful than a single empty text box because the interface teaches the user how to brief an AI system clearly.

The Workshop Noir style gives the product a recognizable identity. Charcoal surfaces create the workbench, bright orange marks actions and focus, and editorial typography keeps the interface legible. The same design language is reused across the Library, pricing, About, Contact, and authentication pages so the product feels like one system rather than a collection of templates.

Chapter three: connect data and member access. The Library is backed by a real catalog, with search, category filters, access filters, sorting, pagination, loading skeletons, retry states, empty states, and prompt actions. Free work orders can be explored immediately, while locked work orders remain protected until the account is unlocked. Copy and Use in Builder move a selected work order into the next step without losing its category or structure.

The account system connects the user identity to saved prompts and access state. Supabase handles authentication, while the application keeps authorization decisions on the server. That separation matters: the browser can display a member state, but protected prompt content and administrative actions must still be checked by the backend. Google OAuth, email and magic-link flows, password recovery, profile details, and durable owner administration were all treated as production concerns rather than demo shortcuts.

Chapter four: link the external platforms. Supabase provides the authentication service and the project database connection. Google Cloud supplies the OAuth client that allows a user to continue with Google. Resend provides branded email delivery for confirmation, recovery, and unlock notifications. The application server uses protected environment variables rather than placing secrets in frontend code. This is the pattern to follow whenever you connect a new platform: configure the provider, store credentials securely, define the callback or webhook, and verify the complete user journey from the live domain.

Manus also makes the development loop visible. We can inspect files, run type checks, build production bundles, test server procedures, correct errors, create checkpoints, and keep the source synchronized with GitHub. The important lesson is that natural-language development does not remove engineering discipline. It makes the feedback loop faster, while validation, secure configuration, and regression testing keep the result reliable.

Chapter five: deploy the product. The source is connected to GitHub, and the main branch is linked to Vercel. Vercel builds the application and aliases the production deployment to the paid domain, promptforge.com.ng. DNS and domain configuration are verified separately from the application itself. After a deployment, we test the real routes with a mobile user agent, check the API path, confirm that the Library loads, and verify that authentication redirects use the paid domain rather than a stale preview URL.

Chapter six: make the site discoverable. Public pages receive clear titles, descriptions, canonical URLs, keywords where appropriate, Open Graph metadata, organization information, and article structured data. PromptForge now includes practical guide and Blog content so the site can answer real search questions about prompt engineering, WhatsApp business workflows, image prompting, freelancing, sales copy, and AI-assisted operations. Static SEO documents are generated for the public routes, including the individual Blog articles, so crawlers can discover useful content directly.
